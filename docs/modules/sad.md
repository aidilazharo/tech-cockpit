- **Trigger question added:** "Are any APIs used in the application?" (yes/no, in API Security). It shows the API security questions and the API inventory, as the conditional rules require.

### Decided in the review (2026-10-25)

- **Hidden facts on removal**: an editor removing a connection or box that carries facts from a section they cannot read (data flow facts, integration connections) is told so, without seeing the facts, and asked first.
- **Picking a TRM application again refreshes it**: re-picking the same application takes TRM's current name and APM number (checked by the API); saving alone keeps the name it was picked with.
- **A cancelled draft's files are deleted** (a stored file another version uses is kept).
- **Sections the reader cannot read show no counts** and drive no hidden-question list for them; only that the section exists.
- **Backup retention values are frozen with the version** at submit: approvers and readers see them without the list permission, and later list edits do not change submitted versions.
- **Local authentication flag** (Authentication method Local custom or Other): shown with icon and text on the SAD's pages and section 8 editor, as a marker and filter on the SAD list, on the TRM application page and in the PDF's Document Details; it needs a justification before submit. The list and the TRM page use the current approved version's answer, else the open draft's (marked "(draft)").
- **Vendors** whose role edits section 2 search every TRM application by name and APM number, like any section 2 editor.
- **Export**: PDF only (no Word export).
- **TRM search** is open to the editors of every diagram that links TRM applications (sections 2, 3 and 12), not only section 2.
- **Resubmitting from the Approval Centre** runs exactly what the SAD's Submit runs (every applicable question answered, fresh TRM and backup snapshots, submitter and date); an incomplete SAD is refused there with the same message (2026-10-25).
- **Who sees the local authentication flag**: only people who can read that SAD's section 5 (Security Architecture Design), everywhere it shows (SAD list marker and filter, TRM application page, the SAD's own pages, the section 8 editor, the PDF's Document Details); for others there is no marker, and the filter leaves out applications whose section 5 they cannot read (2026-10-25). The list filter is "Authentication: Any / Local authentication".
- **The justification for local authentication cannot be marked Not applicable**: it must be written (2026-10-25).
- **The central API inventory's old columns** (environment, single URL, data as text) are dropped and replaced (2026-10-25): the inventory is rebuilt from approved answers at each approval, and there are no real SADs yet.

One living SAD per TRM business application. Every change is a new **version**; a version becomes current only after approval. People see and edit only the **sections their role grants**, for the applications in their scope.

## How questions are answered

- **Typed answers where the template gives choices or the answer is a fact:** single choice, multiple choice, yes/no with details, number, date, link, table. **Rich text** for descriptions.
- **Choice options** are the template's own examples, plus **"Other (specify)" on every single and multiple choice question** (confirmed 2026-10-25). Choice columns inside tables (e.g. classification, priority, scan status) and the TRM fallback choice keep their fixed lists.
- **Show only what applies:** some answers show or hide other questions (rules below). Any shown question can also be marked **Not applicable**, with a reason.
- **Submit needs every applicable question answered** (or marked Not applicable). A completion bar shows progress per section.
- Rich text (2026-10-25): paragraphs, **headings (two levels: Heading, Subheading)**, bold, italic, **underline, strikethrough**, **font size (Small, Normal, Large)**, bullet and numbered lists, **tables** (rows and columns of text) and links (https and mailto). Stored as a document tree, never HTML; printed the same way in the PDF.
- Until Part 2, each diagram slot is a rich-text description; Part 2 adds the diagram and uploads there.

## TRM data in the SAD

- While drafting, TRM-sourced fields (Application Details, Environment Details) show **live and read-only**.
- When a draft is **submitted**, a **snapshot** of them is stored with it, so approvers review exactly what is approved. A returned draft refreshes the snapshot on resubmission (confirmed 2026-10-25).
- The approved version keeps that snapshot, so history shows what TRM held at the time.

## Versions and approval

- **One open draft per application.**
  - Anyone whose role has **Edit on at least one section** can start it. It starts as a copy of the current approved version, or empty for a first SAD.
  - Each person edits only the sections they have Edit on.
- **Submit:** anyone with Edit on at least one section, when every applicable question is answered. While in approval, the draft is read-only.
- **Approval** (seeded rule; admins can change it in the rule editor):
  1. **Application manager**: a person with the new Application manager role whose scope covers the application.
  2. **Solution architect**: a person with the Solution architect role whose scope covers the application.
- **Submit is refused when no one holds the Application manager or Solution architect role covering the application** ("No application manager is assigned to this application"), so the gap is fixed first.
- Return/reject sends the draft back for edits. Resubmission resumes at the returning step (approval engine behaviour).
- **Approved** → it becomes the current version, numbered **1, 2, 3...**; the previous version is kept as history. A draft shows as "Draft of version N".
- **Cancel a draft:** the person who started it (even after losing edit rights), or anyone whose role has "Cancel any SAD draft" (system admins by default), even without reading its sections (confirmed 2026-10-25).
- **Version control table** (template): User, Action, State, Comment, Date, Version, generated from the drafts and approval history: started, submitted, each decision (approved, returned, asked for information, answered), resubmitted, withdrawn, version approved, in date order. **Shown on the version page and in the PDF** (2026-10-25).
- **Diff:** compare any two versions (default: the draft against the current version).
  - Changed answers show before and after; table rows show as added, removed or changed; rich text shows word changes.
  - Only sections the user can view are compared.
  - Diagrams are compared too (phase 8b, below: "Version compare of diagrams").
- **Saving:** per section, with an optimistic lock. A conflicting save is refused with "someone else changed this section" and the latest content.

## Access (RBAC)

- **Per-section View and Edit permissions**, set per role on the Roles screen, within the role's application or portfolio scope.

### draw.io import (phase 6, confirmed 2026-10-24)

- **Who and where**: the editors who draw a slot import into it (**Import draw.io** on the diagram). **Every slot** takes imports: the solution diagram, the infrastructure diagram (into the tab on screen), CI and CD flows and the monitoring diagram.
- **Files**: draw.io's own **.drawio** and **.xml** (compressed or not), **up to 5 MB**. Image exports (.drawio.png, .drawio.svg) are not read.

- **Review first**: after choosing the file, a review lists every container, shape and arrow with what each becomes, and what is skipped and why. **Nothing changes until Import.**

- **Stored at once** when chosen (no Save section needed), removed at once when the author removes one. A diagram must have been saved before files can be added to it (a slot never saved holds none yet, checked under the version's lock).
- **Formats**: .docx, .xlsx, .pptx, .pdf, .png, .jpg/.jpeg, .vsdx, .drawio, **checked by extension and by content** (a renamed file is refused; Office files with macros are refused). Up to **25 MB** each, **up to 20 per diagram**.
- **Opening**: download only, through the API (permission checked, audited), always as an attachment.
- **Storage**: a local folder in development; **Azure Blob Storage** when deployed, reached with the App Service's **managed identity** (@azure/storage-blob, @azure/identity). Unit tests run the Azure driver against a stand-in for the SDK's container client that answers as the SDK does (decided 2026-10-26: Microsoft's Azurite emulator, used before, depends on deprecated packages and brought 230 dev packages).
- **Malware scan** (deployed: Defender for Storage): a new file shows "Being checked for malware" and **cannot be downloaded until Defender reports it clean**. **Production refuses to start without Azure Blob Storage** (`STORAGE_DRIVER=azure-blob`), so files are never served unscanned (2026-10-25). Each file is checked on its own (one that cannot be checked never holds up the others); a file whose stored copy is gone is held as "could not be checked". A file reported malicious is **blocked**, shown as such, **deleted from storage**, and its **uploader and every system administrator** get an in-app notification. Locally there is no scan: files can be downloaded at once.
- **Versions**: files are **carried into a new draft** (the same stored file, not a copy); removing one from a draft never touches an approved version. A stored file is deleted only when no version uses it; one storage refuses to delete is tried again every hour. Approved versions keep theirs (frozen with the version). **A cancelled draft's files are deleted** (2026-10-25; files other versions use are kept).
- **Removing a diagram** that has files asks first ("This diagram has N files. Remove it and its files?"); its files go when the slot is saved. Saving a slot as Not applicable removes its files too.
- **draw.io import**: the original file waits with the import and is **stored under each diagram it created when the author saves** (nothing is kept if the import is not saved).
- **API** (7a, built 2026-10-24): `GET /sad/versions/{id}/uploads` (the files under the diagrams the caller sees; who uploaded is shown only to readers allowed to see people's names in the SAD), `POST /sad/versions/{id}/diagrams/{slot}/{diagramId}/uploads` (multipart `file`), `DELETE /sad/versions/{id}/uploads/{uploadId}`, `GET /sad/versions/{id}/uploads/{uploadId}/file` (refused with 409 while held). Files are stored once (`sad_file`) and referred to per version and diagram (`sad_upload`). Defender's verdict is read every minute from the blob's `Malware Scanning scan result` index tag; a verdict other than clean or malicious (e.g. an error) keeps the file held ("could not be checked").
- **Deployment needs** (for the DevSecOps hand-over): a storage account with a container (default `sad-uploads`); the App Service's managed identity with **Storage Blob Data Contributor** on it **plus permission to read blob index tags** (`Microsoft.Storage/storageAccounts/blobServices/containers/blobs/tags/read`, e.g. Storage Blob Data Owner or a custom role); **Defender for Storage malware scanning on upload** with results written to index tags; settings `STORAGE_DRIVER=azure-blob`, `STORAGE_AZURE_ACCOUNT_URL`, optionally `STORAGE_AZURE_CONTAINER` and `STORAGE_AZURE_CLIENT_ID` (a user-assigned identity). No storage keys.

### PDF diagrams (phase 8a, confirmed 2026-10-25)

- **Drawn by the server** from the diagram data (no screenshots): an SVG per diagram, placed in the PDF by pdfmake. Each section shows its diagrams in the views it shows on screen (section 2: the solution diagram and the Integration view; section 3: the Infrastructure view; section 4: the same, read-only; section 9: the Data flow view; sections 10 and 12: the CI and CD flows and the monitoring diagrams), after the questions of their group. A view drawn in another section names it ("Drawn in “Physical and Network Architecture”.").
- **Each diagram on its own landscape page** (each infrastructure tab, each CI and CD flow, each monitoring diagram), scaled to fit the page and never larger than the canvas at 100%; what follows starts a portrait page again. A slot answered Not applicable shows "Does not apply: <reason>" in the section's flow.
- **Azure icons**: boxes show their icon from **the API's own copy of Microsoft's set** (`NestJS_Backend/src/modules/sad/azure-icons`, written by the web app's `npm run azure-icons` with the web app's copy and the icon names; copied into `dist` by the build), or their generic shape; the kind under the name carries the product name, as on screen. Nothing else is read while rendering (no URLs, no other files).
- **Tables as on screen** after each diagram: grouping boxes, zones or lanes; blocks, boxes or steps; connections or lines with the facts that view shows; section 2's logical matrix after the solution diagram and the technical matrix after both Integration tabs. **Only what the reader may see**: the diagrams, facts and API names come from the same view as the web app's (facts of views the reader cannot read are left out). The PDF's font has no arrow, so a connection's ends are two columns, **From** and **To**.
- **Renamed zones** (infrastructure): the Zones table says "name changed for this diagram".
- **Files**: under each diagram, a "Files (n of 20)" list with name, type, size, who uploaded it ("Restricted" when the reader may not see names), when, and the malware check; the files themselves are not put in the PDF.

### Version compare of diagrams (phase 8b, confirmed 2026-10-25)

- **Per section, changed diagrams only**: on the compare page each section shows, after its changed answers, the diagrams in the views it shows on screen (section 2: the solution diagram and the Integration view; sections 3 and 4: the Infrastructure view; section 9: the Data flow view; sections 10 and 12), but only those that changed. Only sections both versions let the reader view, and only what the reader may see in each version (the diagrams and files views); computed in the web app, no new API.
- **Both versions side by side** (stacked on narrow screens), each picture read-only with **added, removed and changed** zones, boxes, steps and connections outlined in green, red or amber **with the word** ("Added", "Removed", "Changed") on them; a legend above. The earlier picture marks what was removed or changed, the later one what was added or changed.
- **Content only**: items are matched by id; moving a box, resizing a zone or changing the side a line leaves from is not a change. Names (hosting renames included), kind (type, TRM link, Azure icon, who approves), the zone something sits in, a connection's ends, and **each view's own facts** are (Solution view: what it calls, what it does, direction; Data flow view: data objects, classification, frequency; Integration view: every integration fact; other views: label and style). Each view compares its own lines (integration connections in the Integration view, infrastructure lines in the Infrastructure view).
- **Under each pair of pictures, its "Changes (n)" list**: Change, Item (e.g. "Connection: Portal → Policy Admin"), then one column per version with only the changed fields ("What it calls: Policy API v1" and "What it calls: Policy API v2"); an added or removed item lists all its fields on its side.
- **Files** under the diagram added or removed are rows too ("File: Design v2.pdf"); a file carried into the draft is the same file.
- **A diagram in only one version** (a CI or CD flow or monitoring diagram added or removed, or a slot switched to or from Not applicable) is **one row** ("Diagram: Release"), its picture on its side with everything marked, and the other side saying "Not in Version 1" or "Does not apply: <reason>". A changed Not applicable reason is one row too.
- A compare link that does not name both versions says the version is not found.
